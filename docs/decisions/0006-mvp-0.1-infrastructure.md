# ADR 0006: MVP 0.1 infrastructure decisions

- Status: accepted
- Date: 2026-10-25
- Last updated: 2026-10-25

## Decision

For the Flowmark 0.1 reference deployment, use these confirmed choices.
They replace the open provider and access questions in
[MVP-INFRA.md](../../MVP-INFRA.md).

| Area | Choice |
| ---- | ------ |
| Hosted PostgreSQL | Neon. Use ordinary `postgres` + Drizzle, not a Neon-specific API. |
| Dashboard sign-in | Better Auth with email and password. Sign-up creates a workspace, project, and first SDK keys. |
| Access | A signed-in owner sees only projects they belong to. Password reset stays off until email delivery exists. |
| Browser ingestion | Keep the existing SDK path. Keep it write-only, origin-limited, and untrusted. |
| Telemetry retention | 30 days for the reference deployment. |
| Public domain | `flowmark.dev` is already owned. Map landing/docs/dashboard/API as in the infra plan. |
| License | MIT. The repository `LICENSE` file is the source of truth. |

People sign in to the dashboard. Applications authenticate with a project write
key. Those are different credentials.

Local development seeds `local@dev` through Better Auth and attaches that
account to the Fieldwork Operations / local development project. The password
is a loopback fixture documented in the development guide, not a production
account.

## Rationale

The 0.1 target is a small open-source tool and one maintainable reference
deployment, not a public multi-tenant SaaS. Neon covers managed PostgreSQL
without adding a second auth platform. Email and password lets a developer
create an account and sign in to the same project their SDK writes to, without
OAuth or email delivery. Keeping browser ingestion avoids silently dropping a
supported SDK path. A 30-day retention window is enough to start a bounded
cleanup job later.

This supersedes the hosted-provider and dashboard-auth intent in
[ADR 0002](./0002-supabase-postgres-and-auth.md), and it replaces the earlier
Google-only sign-in choice in this ADR. Drizzle, `packages/db`, and ordinary
PostgreSQL via `DATABASE_URL` remain.

## Consequences

- Do not add Supabase Auth, GitHub OAuth, or Google sign-in in this increment.
- Do not enable password recovery until a real email sender exists.
- Do not delete or merge browser-key tables just to simplify the first
  release.
- Do not authenticate dashboard reads with a shared demo read key.
- Implement a 30-day telemetry cleanup only when the data-lifecycle increment
  starts. The period is decided; the job is not built yet.
- Self-hosters may still use any PostgreSQL. Neon is the reference, not a
  requirement imposed on every install.
