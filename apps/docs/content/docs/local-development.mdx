title: Local development
description: Run the Flowmark API, database, and dashboard on your machine.

Use this stack while you instrument an application locally. Hosted Flowmark
is the product path; these services are what the repository runs today.

## Repository setup

Requires Node.js 20.19+, pnpm 10.18.1 and Docker Compose. Local PostgreSQL
runs through Compose; applications run natively.

```sh
pnpm install
pnpm dev:setup
pnpm infra up
pnpm db:setup
pnpm dev
```

Open the dashboard at `http://localhost:3001` and the harness at
`http://127.0.0.1:3004`. Use `pnpm infra status` / `pnpm infra logs` for
diagnostics and `pnpm infra down` to stop this checkout's database while
retaining its volume. Subsequent schema updates use `pnpm db:migrate:local`.
`pnpm test:integration` uses separate disposable PostgreSQL and never resets
development/demo data. Existing env files and databases are never rewritten
or removed by setup.

## Services to operate

- **Flowmark API:** accepts private server events and public browser events,
  hosts Better Auth, and authorizes dashboard reads. Configure its PostgreSQL
  `DATABASE_URL` and a `BETTER_AUTH_SECRET` for hosted use. Instrumented
  applications use `FLOWMARK_API_URL` and `FLOWMARK_API_KEY` to connect to this
  API; those are SDK client settings, not a dashboard login.
- **PostgreSQL:** stores users, sessions, projects, hashed keys, workflows,
  runs, and append-only event history. Back up and protect this database as
  telemetry data.
- **Dashboard:** people sign in with email and password. The dashboard
  same-origin-proxies `/api/auth/*`, `/api/register`, and `/api/trpc/*` so the
  session cookie stays first-party. Reads are scoped to projects the signed-in
  user belongs to.

Sign-up creates the account only. Create the first project and server write
key in onboarding or Settings. The repository's seeded `local@flowmark.test` account is a
loopback fixture for the
operations project, not a production owner. Password reset is not available
until you add email delivery. Do not expose a dashboard configured with demo
mode or a shared demo credential to the public internet.

## Configure keys safely

Keep private server-write keys in server-side secret storage. Never place them
in browser bundles, frontend environment variables, or build logs. Browser
instrumentation requires a separate public browser key, restricted to exact
origins and rate limited per key; its events remain untrusted input.
Programmatic API reads may use a project read key; the dashboard itself uses
the signed-in session.

Before handling real data, add your own authentication, rate limiting,
provisioning, backups, retention and deletion policy, and monitoring. Rotate a
write key from Settings when a credential may be exposed. Test these controls
in a non-production project. Do not use the repository's public local-demo
credentials with customer data.

## Local development harness

The repository's invoice, inventory and order operations harness is a
loopback fixture for contributors. It uses fixed development projects and
development-only credentials. Setup, ports, and PostgreSQL workflow live in
the internal contributor guide.
