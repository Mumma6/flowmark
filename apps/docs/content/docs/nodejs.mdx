## A short-lived script

Install `@flowmarkdev/node` and set `FLOWMARK_API_KEY`. Hosted delivery is the
default; use `FLOWMARK_API_URL` for a local or staging API. Scripts inherit their
environment; load any `.env` file before creating the client.

```ts
import { createFlowmark } from "@flowmarkdev/node"
import { importInvoices } from "./business/import-invoices"

const flowmark = createFlowmark()
try {
  console.log(await importInvoices(flowmark))
} finally {
  try {
    await flowmark.shutdown()
  } catch (error) {
    console.error("Flowmark delivery failed", error)
  }
}
```

The inner catch makes delivery failure visible while preserving the business
result or exception. Missing credentials or invalid configuration throw when the
Node client is created.

## Share business logic with Next.js

The business function accepts the client capability it uses. It imports only SDK
types, so a Next request and a CLI can call the same implementation:

```ts
import type { FlowmarkClient } from "@flowmarkdev/node"

export function importInvoices(flowmark: Pick<FlowmarkClient, "workflow">) {
  return flowmark.workflow("invoice.import", async (flow) => {
    const result = await flow.operation("save-invoices", () => saveInvoices())
    flow.step("saved")
    flow.done({
      outcome: result.rejected > 0 ? "partial" : "complete",
      result: { imported: result.imported, rejected: result.rejected },
    })
    return result
  })
}
```

`saveInvoices()` is your existing application function. Normal callback return
requests completion; an unexpected exception records a generic failure and
rethrows the original value. Explicit `done()` supplies the business result.
Use `fail({ code, outcome?, result? })` for a known failure with safe details.

A [Next entry point](/docs/nextjs) passes its Next client and leaves delivery to
the adapter. The CLI passes its Node client and drains at the process boundary.
No runtime detection or custom adapter is needed.

## Long-lived workers and servers

Reuse one process client across jobs. `await flowmark.flush()` drains pending
evidence without closing it. Call `shutdown()` from the application's existing
shutdown path after all work finishes. The SDK installs no signal handlers and
does not exit the process.

Shutdown releases delivery resources; it does not finish business work or invent
terminal events. Repeated shutdown calls share the same result; starting work on
a closed client throws. Explicit drains can reject after delivery failures. See
[delivery](/docs/delivery).

An application retry starts a fresh run. Continue the same ID only while that
execution remains unfinished. Use [manual workflow markers](/docs/reference/workflow)
for a process spanning multiple invocations; see [attempts](/docs/reference/attempts)
for optional retry links.
