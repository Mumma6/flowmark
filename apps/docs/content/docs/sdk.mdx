## Set up with your AI agent · recommended

Create a project in Studio and save its ingestion write key. In onboarding, open
**Get setup instructions** and choose **Copy setup prompt**. Paste it into
your AI agent's chat with your application's repository available. You can reopen
the setup guide from the Studio account menu later.

The prompt asks your AI agent to fetch the instrumentation guide from your
Flowmark API, install the SDK and help instrument one useful
process. Your agent uses its normal coding tools to edit your repository. Set the
write key in your application's server environment yourself.

Choose **Open Studio** whenever you are ready; onboarding does not wait for SDK
installation, a release or application traffic. Install and deploy on your own
schedule. When the instrumented process runs and sends evidence, its executions
appear in Studio. **No MCP connection is needed for setup.** You can also follow
the manual instructions below.

Once your application reports evidence, [connect Cursor with MCP](/docs/mcp) if
you want it to investigate executions, failures and business outcomes. This is a
separate read-only connection.

## Manual SDK setup

No AI client is required. Follow these steps to instrument the application yourself.

### Before you start

You need a running Flowmark API, a project server-write key, and the SDK.

```bash
npm i @flowmarkdev/node
```

### 1. Configure the server

Set these in your server environment, not in browser-visible variables:

```bash
FLOWMARK_API_KEY=<your-project-server-write-key>
```

Hosted delivery is the default. Set `FLOWMARK_API_URL` for local or staging APIs;
use the API origin, not `/v1/events`. See [configuration](/docs/configuration).

### 2. Create one shared client

```ts
// lib/flowmark.ts (server only)
import { createFlowmark } from "@flowmarkdev/node"

export const flowmark = createFlowmark()
```

Using Next.js? Import from `@flowmarkdev/node/next` instead and follow the
[Next.js guide](/docs/nextjs) for automatic request-lifecycle delivery.

### 3. Add markers to an existing function

`loadInvoices` and `saveValidInvoices` below are your application's
existing helpers, not SDK APIs. No business work moves into Flowmark.

```ts
import { flowmark } from "./lib/flowmark"

function importInvoices(batchId: string) {
  return flowmark.workflow(
    "invoice.import",
    async (run) => {
      const invoices = await run.operation("load-invoices", () =>
        loadInvoices(batchId),
      )
      run.step("source-loaded", { properties: { count: invoices.length } })
      const result = await run.operation("save-invoices", () =>
        saveValidInvoices(invoices),
      )
      run.done({
        outcome: result.skipped > 0 ? "partial" : "complete",
        result: { imported: result.imported, skipped: result.skipped },
      })
      return result
    },
    { properties: { batchId } },
  )
}
```

The callback completes on return and records unexpected failure while preserving
the original exception. `step()` records a milestone; `operation()` measures work;
`done()` supplies the business outcome and result. Use manual markers for a
process that continues across requests.

### 4. Drain delivery at a process boundary

Markers queue delivery automatically. In a plain Node.js script or worker,
drain the client before the process exits:

```ts
try {
  await flowmark.shutdown()
} catch (error) {
  console.error("Flowmark delivery failed", error)
}
```

Do this once at the job/process boundary, not inside every shared function.
For a long-running process, use `flush()` without closing the client.
An explicit drain can reject; handle that separately from the business result.
The [Next.js adapter](/docs/nextjs) handles draining after the response.

### 5. Inspect reported evidence

Your application may not run this process until hours or days after deployment.
Studio does not need to stay open: it shows **No recorded executions** until the
application reports one. **Setup instructions** reopens the guide whenever you
need it.

For an optional delivery check, use an existing test or safe application action
that runs the actual instrumented process. Local checks alone do not prove a
deployment or delivery. If there is no safe way to run it now, wait for normal
activity; do not create artificial executions or trigger business operations just
to populate Studio.

Once an execution arrives, open **Explore** in Studio with the same project selected. Choose `invoice.import`
to see its execution history, then open the execution. **Outcome** shows reported
results, including imported and skipped counts; **Timeline** shows milestones,
operations and failures. If Cursor is connected, ask it to explain that execution
using Flowmark MCP and follow its supporting Studio link.

If an expected execution is missing, follow [troubleshooting](/docs/troubleshooting). A missing
terminal event is not proof the business operation failed.
