---
title: Security and privacy
description: Protect keys and choose safe workflow telemetry.
---

Flowmark stores the workflow names, steps, context, errors, and result summaries
that your application explicitly sends. Treat them as application data, not as
anonymous or harmless metadata.

## Keep credentials on the right side

- Use the private server-write key only in Node.js or server-only modules.
- Dashboard readers sign in with email and password. A project read key is
  only for programmatic API queries, not for the dashboard UI.
- Browser keys are public by design and can submit browser telemetry only.
  They cannot read data or authorize private server writes.
- Configure exact browser origins and rate limits. CORS and origin checks are
  not user authentication. Treat browser events as untrusted telemetry.

Never place a private key in a `NEXT_PUBLIC_*` variable, browser config file, or
client bundle.

## Choose what to record

Use stable names and small JSON-safe properties. Avoid secrets, credentials,
payment information, request bodies, raw exception objects, stack traces, and
unnecessary personal data. A safe example is `{ provider: "backup" }`; an
order ID can still be personal data in your context and retention model.

Use stable error codes with an optional message that you have reviewed. Do not
send the full error object. Set `handled: true` when your application recovered.

Workflow properties and results are bounded to depth 5, 128 keys, 128
characters per key, 2,048 characters per string, and 16 KiB encoded per object.
Keep payloads well below these limits and send only fields that help investigate
the run.

## Data ownership and operation

Dashboard sign-in is Better Auth email and password. Retention cleanup is not
enforced by the product yet. See
[local development](./local-development) for the current stack.

## Keys and rotation

Server and browser keys are stored as hashes. A new secret is shown once and
cannot be read back. Emergency rotation of a server write key replaces that
key in one step: after it is saved, the previous secret is rejected. A request
that was already authorized may still finish. Rotation does not leave the old
key valid while you deploy.

To replace a key without downtime, create a new write key, update the
application, then revoke the old key.

If the page never shows the replacement secret, the old key is already revoked
and the new secret cannot be recovered. Revoke the listed replacement and
create another key. Rotating the old key again does not reveal the secret.

A project name is only a label. The `environment` an SDK reports is telemetry,
not a permission boundary. Existing programmatic read keys stay valid. A new
project receives a write key only.

## Operation callback exceptions

Without a mapper, operation callbacks still record bounded structured failures
and `Error.message`. Do not assume arbitrary exception messages are safe.
Use per-operation `mapError` to choose an existing failure code, safe message and
retryability without appending the original exception message or stack. Mapper
failures retain only a bounded diagnostic reason and emit a generic failure;
the application receives its original rejection unchanged. See
[operation error mapping](/docs/reference/operation).

This does not redact arbitrary context/results, sanitize fields deliberately
returned by your mapper or control application logging. Keep mappers synchronous,
small and nonrecursive. Expected domain rejections should be result/reason counts;
recovery from a technical operation failure may still end in a completed run.

## Expectation evidence

[Expected confirmations](/docs/reference/expectations) require the accepting `expectations-v1` server and migrations. Resolve/cancel are explicit, project-scoped evidence reports and may follow a terminal run without changing its outcome/result. Direct browser evidence stays untrusted; the existing generic server-key proxy rejects expectation events. Deadlines are evaluated on read from server observation, without background notifications or a retention extension.
