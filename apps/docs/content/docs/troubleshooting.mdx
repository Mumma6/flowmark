title: Troubleshooting
description: Diagnose missing runs, incomplete timelines, and reported failures.

## Resume setup or recover a lost key

Open **Reopen setup guide** from Studio's Getting started checklist, or use
**Connect** for Cursor and manual SDK setup. During
initial setup, progress is saved to your account; refreshing does not preserve
the one-time key value.

Choose the project you own before continuing. Setup requires a **server write
key** for that project; read keys and browser keys cannot authorize server SDK
ingestion. If you lost the secret or revoked the key, open **Instrument one process**, expand **Need a new write key?** and
choose **Create another server write key**. Existing keys keep working. Save the
new value in your server environment, never in browser code or local storage.

A failed project, key or run request shows an error with a retry control. It is
different from an empty project. If copying is unavailable, select and copy the
displayed text manually. Account, security and setup help remain reachable from
the setup header.

A successful Cursor connection check verifies read access, even with an empty
process list. Installing the SDK or finishing the guide does not prove that your
application sends evidence. The run
step checks for a received run in the selected project. You can finish setup
before reporting a run and return to the guide later. If a run remains missing,
check the project, API origin, key permissions and revocation state below;
rate-limited requests need to respect the server's retry guidance. Flowmark
does not execute your application to generate a test run.

## Studio access or session errors

Losing access to one project does not necessarily end your sign-in session.
Choose another permitted project or use **Access help**. Studio confirms the
session before presenting **Sign in again**. If the auth service is unavailable,
the failed request stays an error; it is not treated as proof of session expiry.

When a session has ended, Studio cancels pending queries, clears its private
query cache and offers sign-in with a known local return page. It does not
repeat your previous mutation after sign-in. Check the current state before
trying a write again.

Help offers the existing private incident mailbox as well as public issues.
**Prepare optional support details** creates a local preview containing only
the error code and context you enter. Nothing is attached or sent automatically.
Review it before copying, and leave out credentials, email callback links,
personal data and private telemetry.

## A run is missing

1. Confirm the workflow marker runs in application code and uses a semantic
   workflow name.
2. Check that the server process has the private `FLOWMARK_API_KEY` and the
   correct `FLOWMARK_API_URL`.
3. Check API availability, key permission, and persistence health. The API
   acknowledges server ingestion only after it stores the event.
4. For browser delivery, verify the public browser key, the exact request
   `Origin`, and API CORS configuration. Browser keys cannot use the server
   ingestion endpoint.

Delivery is best-effort. The SDK's in-memory queue is bounded; a process exit,
browser shutdown, or network interruption can lose telemetry. Instrumentation
failure should not change the result of your business operation.

## A run stopped before `done()` or `fail()`

An incomplete timeline is not proof that the business operation failed. The
process, tab, or telemetry delivery may have stopped before a terminal marker
was stored. Compare the available events with your application logs and traces,
then add a marker at the decision point you need to inspect.

## A run is failed

`fail()` is an outcome reported by your application code. Inspect its error
code, safe message, retryable flag, and preceding milestones. Your application
decides whether to retry.

## Completion is waiting on an operation

`done()` waits for already-open operation handles. Close each handle using
`operation.done()` or `operation.fail()`, or use the callback overload to close
on settlement. A callback rejection does not automatically fail the whole run.
See [operation lifecycle](/docs/reference/operation#overlap-and-completion).

## A recovered error appears

Use `error({ handled: true, ... })` only for errors your code recovers from.
The error is recorded separately from the run outcome, so the run can later
complete with `done({ result })`. If recovery does not succeed, emit a
terminal error and `fail(...)`.

## Configuration errors

- **Server key missing:** add the private `FLOWMARK_API_KEY` to the server
  environment; do not replace it with a public browser key.
- **Browser origin rejected:** add the exact frontend origin to the browser
  key's allowlist. Avoid wildcard CORS as a workaround.
- **No database connection:** verify PostgreSQL reachability and the API's
  `DATABASE_URL`.
- **Unexpected result data:** check that properties and results contain only
  bounded, plain JSON-safe values.
- **Diagnostics not visible:** configure `onInstrumentationError` or inspect SDK
  warning logs. Explicit `flush()` and `shutdown()` can also reject; handle them
  without masking the application's result. See [delivery](/docs/delivery).

For the current stack and authentication, see
[local development](./local-development) and
[security and privacy](./security-privacy).

## Callback reports HTTP 409 after completion

Check whether another request already closed the same workflow and external
run ID. EVENT_CONFLICT means the new report was not recorded; it does not change
the existing final result. RUN_NOT_FOUND instead means no start was recorded in
the credential's project. Do not complete a submission before an expected
application callback if they belong to one execution. Application retries need
a new execution ID; transport retries retain their envelope event ID. Flowmark
does not deduplicate or retry the underlying business work.
