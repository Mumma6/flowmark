---
title: progress
description: Record an absolute snapshot of work completed so far.
---

## Signature

```ts
run.progress(progress: WorkflowProgress): void
```

## Example

```ts
let updated = 0
for await (const page of fetchProductPages(supplierId)) {
  await updateStock(page)
  updated += page.length
  run.progress({ completed: updated, total: 1000, unit: "products" })
}
```

The helpers are application code. Call after the work whose progress you want
to report, not before it.

## Fields

| Field       | Type     | Validation                                                      |
| ----------- | -------- | --------------------------------------------------------------- |
| `completed` | `number` | Required nonnegative safe integer                               |
| `total`     | `number` | Optional nonnegative safe integer; must be at least `completed` |
| `unit`      | `string` | Optional non-empty string, max 64 characters                    |

Snapshots are absolute, not increments. Two reports of `completed: 100` do not
mean 200 items. By default (`delivery.progress: "all"`), every valid call queues its own event,
subject to delivery and capacity limits. For bulk work, opt into
`delivery: { progress: "latest" }` on Node, Next.js or browser clients.

With `"latest"`, adjacent unsent progress for one handle is replaced by the latest
whole absolute snapshot, including its timestamp. Omitted total/unit fields are
not inherited. Every call is validated before replacement; invalid calls still
reach diagnostics and never erase the previous valid snapshot. In-flight events
are immutable. Any intervening marker or flush seals the previous snapshot in
its existing order. Completion follows the last queued progress.

This reduces historical progress density; it does not aggregate counts or
coalesce business `report()` snapshots. Report progress per useful batch even
with this option. Under pressure across many handles, bounded capacity can still
drop new snapshots; see [delivery limits](/docs/delivery).

## Interpretation and invalid input

The latest report is evidence from the application, not a heartbeat, prediction,
or guarantee of the current database state. Progress does not complete a run.

Invalid snapshots are rejected through instrumentation diagnostics, not capped
or silently repaired. Snapshots after completion request or failure are ignored.
See [delivery and diagnostics](/docs/delivery).
