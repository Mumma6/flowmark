---
title: workflow and runId
description: Start a new execution under a stable workflow name.
---

## Signature

```ts
flowmark.workflow(name: string, options?: WorkflowRunOptions): Flow
```

Each call immediately queues a start event and returns a run handle.

## Example

```ts
const run = flowmark.workflow("invoice.import", {
  properties: { batchId },
  environment: "production",
  release: "2026.10.2",
})
console.log(run.runId)
```

## Options

| Field           | Type                 | Behavior                                                          |
| --------------- | -------------------- | ----------------------------------------------------------------- |
| `id`            | `string`             | Execution ID; generated if omitted. Reuse it to continue this run |
| `properties`    | `WorkflowProperties` | Bounded context on the start event                                |
| `environment`   | `string`             | Overrides the client default                                      |
| `release`       | `string`             | Overrides the client default                                      |
| `correlationId` | `string`             | Explicit grouping; nonblank, max 128 characters                   |
| `parentRunId`   | `string`             | Parent's external run ID; nonblank, max 200 characters            |

Use stable names such as `invoice.import`; put instance IDs in properties.
Reuse `id` across requests of the _same_ execution. Do not reuse an order ID
as the run ID across retries or later jobs.

## Returned handle

`Flow` exposes `runId`, `step`, `operation`, `progress`, `error`,
`setProperties`, `done`, and `fail`.

`runId` is the external SDK identifier, not the dashboard database UUID.
Propagate it explicitly if you need [parent links](/docs/concepts/related-runs).

## Errors and lifecycle

Invalid start context/configuration or a shut-down client can throw
`FlowmarkConfigError`. Delivery errors after starting use instrumentation
diagnostics. `workflow()` after shutdown is not supported.
See [delivery and diagnostics](/docs/delivery).

## Qualified execution reference

Node, Next and browser exports include the plain `WorkflowRunReference` type:
`{ readonly workflow: string; readonly runId: string }`. Persist/transport it in
your application and resume with `workflow(ref.workflow, { id: ref.runId })`.
Validate and authorize application callbacks yourself. This does not query remote
state, transmit TypeScript types, coordinate work or grant project access.

A repeated start is acknowledged as ignored and never rewrites the original
properties/environment/release/correlation/parent metadata. Accepted amendments
use `setProperties`. A later attempt uses a fresh ID. See
[cross-request terminal decisions](/docs/concepts/runs#terminal-decisions).

## Explicit application-owned attempts

See [Attempts and retries](/docs/reference/attempts) for operation `attempt: { groupId, number }`, qualified new-run `retryOf` links, bounds, project scoping and the required `attempts-v1` accepting-server acknowledgment. Supplying these options is explicit opt-in; deploy accepting storage/API/readers before enabling them. Transport retries remain separate from business attempts.
