---
title: createFlowmark
description: Create a configured client for the runtime where the work happens.
---

## Node.js

```ts
import { createFlowmark } from "@flowmarkdev/node"
import type { FlowmarkClient, FlowmarkConfig } from "@flowmarkdev/node"

// Signature: createFlowmark(config?: FlowmarkConfig): FlowmarkClient
const flowmark = createFlowmark({
  environment: "production",
  release: "2026.10.2",
})
```

| Option                   | Type                               | Required                                   |
| ------------------------ | ---------------------------------- | ------------------------------------------ |
| `apiKey`                 | `string`                           | Option or `FLOWMARK_API_KEY`               |
| `apiUrl`                 | `string`                           | Option or `FLOWMARK_API_URL` in production |
| `environment`            | `string`                           | No                                         |
| `release`                | `string`                           | No                                         |
| `delivery`               | `{ progress?: "all" \| "latest" }` | No; defaults to per-call progress          |
| `onInstrumentationError` | `(error, event) => void`           | No; defaults to warning logs               |

The client returns [`workflow()`](/docs/reference/workflow),
[`flush()`, `shutdown()` and `deliveryHealth()`](/docs/reference/delivery). Reuse it across work;
close it at the process boundary. Creating it validates server settings and
can throw `FlowmarkConfigError`. Starting a workflow can also throw for invalid
run context or a closed client.

See [configuration](/docs/configuration) for URL rules and precedence.

## Next.js

```ts
import { createFlowmark } from "@flowmarkdev/node/next"

const flowmark = createFlowmark()
// Exposes workflow/definition and expectation settlement methods; no manual drains.
```

Accepts the same server options but creates a request-scoped delivery client
when a workflow starts or an expectation settlement is reported. Call it only in supported Route Handler or
Server Action contexts; `after()` drains after the response.
Pass `onDeliveryHealth(health)` to the Next `createFlowmark()` or `defineConfig()` to observe
final request-local counters after each workflow drains; it runs on failed drains
too and callback errors are contained. This option belongs to `NextFlowmarkConfig`.
Invalid configuration/context can throw when starting the run.
See [Next.js integration](/docs/nextjs).

## Browser

```ts
import { createFlowmark } from "@flowmarkdev/node/browser"
import type { BrowserFlowmarkConfig } from "@flowmarkdev/node/browser"

const flowmark = createFlowmark({
  publicKey: "fm_browser_...",
  apiUrl: "https://your-flowmark-api.example",
})
```

| Option                   | Meaning                                                 |
| ------------------------ | ------------------------------------------------------- |
| `publicKey`              | Public browser-write key for direct ingestion           |
| `apiUrl`                 | API origin, required with `publicKey`                   |
| `proxyPath`              | Same-origin absolute route; defaults to `/api/flowmark` |
| `environment`, `release` | Default run metadata                                    |
| `delivery`               | Shared opt-in progress policy; default `"all"`          |
| `onInstrumentationError` | Optional delivery/validation failure callback           |

Direct settings and `proxyPath` are mutually exclusive. Creation is SSR-safe;
the first `workflow()` validates browser context/settings and must run in an
event handler or effect. No React provider or environment-file loader is needed.
See [browser integration](/docs/browser).
