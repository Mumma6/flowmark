---
title: done and fail
description: Report a terminal outcome without returning or throwing on behalf of your function.
---

## Signatures

```ts
run.done(options?: WorkflowDoneOptions): void
run.fail(options: WorkflowFailOptions): void
```

## Completion

```ts
run.done({ outcome: "partial", result: { imported: 988, skipped: 12 } })
```

`result` is optional. Prefer a small reviewed summary — imported and skipped
counts, a shipment id — over passing a raw function return value.

If operations are still open, completion waits for their handles to close.
The first completion request wins and its result is preserved. New run markers
are ignored while completion is pending; existing operation handles can close.
Calling `fail()` supersedes pending completion.

## Failure

```ts
run.fail({
  code: "SUPPLIER_SYNC_FAILED",
  message: "Supplier inventory could not be synchronized",
  retryable: true,
  outcome: "partial",
  result: { updated: 8, remaining: 4 },
})
```

| Field       | Meaning                                             |
| ----------- | --------------------------------------------------- |
| `code`      | Required non-empty stable code, max 128 characters  |
| `message`   | Optional safe description, max 2,048 characters     |
| `retryable` | Optional application policy for the failure         |
| `result`    | Optional bounded business summary, same as `done()` |

`code` is required. Do not pass a bare string. Attach `result` when the
application already knows what was produced before the failure — partial
counts, reserved work, or identifiers needed to continue.

## Your function is still in charge

Neither method returns from your function, throws your original exception,
retries, or rolls back work:

```ts
try {
  const result = await importInvoices()
  run.done({ result: { imported: result.imported, skipped: result.skipped } })
  return result
} catch (error) {
  run.fail({ code: "IMPORT_FAILED" })
  throw error
}
```

Once terminal, later calls on that local handle are ignored. For independent
handles/requests, the server accepts only the first terminal. A new terminal
event ID then returns HTTP 409 `EVENT_CONFLICT`; a replay of the stored envelope
ID returns a duplicate acknowledgment. Ordinary late markers return an explicit
ignored acknowledgment. Local pending operation waits are not global locks.
Final outcome/result are never replaced by a later terminal. Previously stored
mixed-terminal history is preserved. See [terminal decisions](/docs/concepts/runs#terminal-decisions).

## Business outcome

`outcome` is an optional canonical business code on both terminal methods,
independent of execution status and `result`. A completed run may be `partial` or
`no-availability`; a failed run can still report useful committed work. An absent
outcome means unknown. Codes match `^[a-z][a-z0-9_-]{0,63}$` and are not normalized.
Invalid marker values use instrumentation diagnostics without throwing into
application work. Existing calls without outcomes keep their behavior.

Only the terminal event's explicit `outcome` field defines the business outcome.
Fields inside `result` are ordinary application data and are never mapped to it. Browser-reported results remain untrusted evidence.

In the workflow view, create immutable presentation revisions for ordered counts,
units, categories and nested reason distributions. Set
`properties.definitionRevision` on the **original start** to select a revision.
Use a new revision when units or meaning change; context amendments cannot switch
it. Runs without an explicit revision use the default result view. Missing and wrong-type fields are shown separately from zero.
Raw results stay available. Declarations do not verify results or reconcile counts.

`outcome` is included in `@flowmarkdev/node` and `@flowmarkdev/core` 0.2.0.
Use it only against a server that accepts the field. An older server reports a
delivery failure instead of storing a stripped outcome. Reports and typed
workflow definitions are in the same package version.
