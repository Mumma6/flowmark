---
title: operation
description: Measure a named unit of work and record its duration.
---

## Signatures

```ts
run.operation(name: string, options?: WorkflowOperationOptions): WorkflowOperation
run.operation<T>(
  name: string,
  callback: () => PromiseLike<T>,
  options?: WorkflowOperationOptions,
): Promise<T>
```

## Promise callback

```ts
const receipt = await run.operation("charge-payment", () => chargeCustomer())
```

The SDK starts an operation, closes it when the callback settles, and preserves
its return value. If it rejects, the operation is marked failed and the
**same original cause is rethrown**. A thrown `{ code, message?, retryable? }`
is copied into telemetry. An `Error` is recorded as `operation_failed` plus
its message. Synchronous callback throws are also recorded as operation
failures.

`options.properties` attach bounded JSON to the operation start event, the
same way step properties stay on that step.

If the operation fails, decide whether to recover or call
[`fail()`](/docs/reference/completion) for the run.

## Explicit handle

```ts
const operation = run.operation("reserve-stock", {
  properties: { warehouse: "eu-west" },
})
try {
  await reserveStock()
  operation.done()
} catch (error) {
  operation.fail({ code: "OUT_OF_STOCK", retryable: false })
  throw error
}
```

| Member                | Meaning                                            |
| --------------------- | -------------------------------------------------- |
| `operationId`         | Unique UUID for this operation's events            |
| `done(): void`        | Record success and monotonic duration              |
| `fail(failure): void` | Record a structured failure and monotonic duration |

`failure` is `{ code, message?, retryable? }`. `code` is required. Do not
include sensitive exception messages.

## Overlap and completion

Operations are independently identified siblings. They may overlap and share a
name; nested operation relationships are not supported.

If `run.done()` is called while operations remain open, run completion is
deferred until the final handle closes. The first completion request and result
win. Other run markers are then ignored, but the existing handles can close.
An unclosed handle can leave the run open indefinitely.
`run.fail()` supersedes pending completion.

Calling an operation callback after the run is terminal still executes your
callback. The run stays closed.

## Opt-in safe callback errors

```ts
await run.operation("crm-request", () => crm.request(), {
  mapError: (_cause) => ({
    code: "CRM_UNAVAILABLE",
    message: "CRM temporarily unavailable",
    retryable: true,
  }),
})
```

`mapError?: OperationErrorMapper` is synchronous: `(cause: unknown) => WorkflowFailure`.
It is available on Node, Next.js, browser and custom-transport callback overloads.
The mapper receives the original cause, but the application still catches that
exact original object/value. Callback success and return inference are unchanged.
Only validated mapped `code`, `message?` and `retryable?` fields enter telemetry;
extra fields are discarded and original exception details are never appended.

When omitted, the existing automatic structured/Error.message conversion above
remains. Manual `operation.fail(...)` is unchanged and does not invoke the mapper.
Throwing/invalid mappers produce a bounded `FlowmarkErrorMappingError` diagnostic
and generic `{ code: "operation_failed" }` telemetry, never an operation success
or raw-message fallback. Explicit drains report these failures; Next contains and
logs its automatic drain failure. The local failed-health counter includes mapping
failures. A mapper must not return a Promise; async results are rejected without
waiting, and rejected promises are contained.

The diagnostic contains only a reason (`threw` or `invalid`) plus safe event
context; neither the original cause nor invalid mapper result is retained.
Diagnostic context is not an additional emitted event. Throwing diagnostic
callbacks are contained as usual. A mapped operation failure still does not
fail the workflow: recover if appropriate and report your final result with
`done()` or deliberately fail the run.

Use result/reason counts for expected domain rejections (such as an invalid
email), and mapped operation failures for technical failures (such as a CRM
request failing). This is developer-controlled field selection, not a global
redactor for arbitrary properties, results or your own logs.
