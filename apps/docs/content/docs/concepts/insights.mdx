Flowmark turns marked processes into numbers operations can act on, then
lets you open one execution for the story behind those numbers.

## Process-level insight

The dashboard overview and each workflow page summarize recorded runs:

| Insight         | What it measures                                                    |
| --------------- | ------------------------------------------------------------------- |
| Volume          | How many times the process ran                                      |
| Daily trend     | 30-day charts of completed vs failed volume and median/p95 duration |
| Week over week  | Last 7 days versus the previous 7                                   |
| Success rate    | Completed share of finished runs                                    |
| Failed runs     | How many executions called `fail()`                                 |
| Median duration | Typical time from start to `done()` or `fail()`                     |
| p95 duration    | How long the slower finished runs take                              |
| Slow operations | Named `operation()` work ranked by total recorded time              |
| Failure codes   | Which `fail({ code })` values appear most                           |

Duration is workflow performance: how long the business process took.
Named [`operation()`](/docs/reference/operation) calls add their own start,
end, and monotonic duration, so you can see which unit of work was slow.

## Run-level insight

Open one execution when the numbers need a story:

| Insight      | Where it comes from                                |
| ------------ | -------------------------------------------------- |
| Outcome      | `done()` or `fail()`                               |
| Result       | The JSON summary attached to that terminal call    |
| Progress     | The last `progress()` snapshot                     |
| Operations   | Each named unit of work, with duration             |
| Compare      | This run versus the last 20 of the same workflow   |
| Errors       | `error({ handled })` events and operation failures |
| Related runs | `correlationId` and `parentRunId` you passed       |

Compare shows this run's duration against the peer median and p95, plus
each earlier run's status and duration delta.

Use a result when someone needs counts or identifiers:
`{ imported: 988, skipped: 12 }` or `{ shipmentId, paid: true }`.
Use progress while work is still moving:
`{ completed: 600, total: 1000, unit: "records" }`.

## What to report so the numbers stay useful

- Give each process a **stable name**, such as `checkout.order`.
- Put the order or batch id in **properties**.
- Wrap the work that can be slow in **`operation()`**.
- Attach a small **result** on both success and failure.
- Call **`fail({ code })`** with a stable code when the process fails.

See [workflows and runs](/docs/concepts/runs) for the lifecycle, and
[reading the dashboard](/docs/concepts/dashboard) for where these numbers
appear.

## Reported business outcomes

Each workflow has a business outcome panel with explicit definition, UTC start
cohort, field coverage and independent technical failure counts. Select current
and previous intervals (up to 31 days each), an aggregatable result field and
optionally a bounded configured dimension. Daily rows show reported count/reason
totals for observed start cohorts. Partial work reported on failed runs still
contributes; `report()` snapshots never become final observations.

Enable aggregation in a **new immutable result revision** using `aggregate: true`.
For categories/reasons, also declare 1–20 distinct `values`. Existing presentation
revisions remain presentation-only. Original-start `properties.definitionRevision`
selects the definition; later context amendments do not change it.

The cohort is start >= after and start < before, in UTC. Each run/attempt counts
once, so retries with a new run ID count again. Late terminal evidence can change
a historical start cohort. Canonical outcome counts use all finished runs; field
totals use only compatible finished results, including failed-with-result.
Missing results/fields/revisions, wrong types and unknown categories are visible
coverage gaps, not zeroes. Counts mean reported items across runs, not unique
entities. Absent reason keys remain unknown; an explicit zero is a known zero.

Choose numerator and denominator count fields for a weighted ratio: sum of the
numerators / sum of the denominators over the same jointly valid finished runs.
For 1/2 and 9/100, the ratio is 10/102, not an average of per-run percentages.
An overall zero denominator or no valid pairs is unavailable. Ratios may exceed
one and are not inferred business-success scores.

Outcome/category/reason links open historical Run Explorer evidence with the
same workflow, period, dimension, release and definition/result selection. Numeric
predicates support equals/at least/at most; categories support exact equality.
Reason evidence requires a fully valid declared map, matching the aggregate.

Two releases can be compared in the current interval when all finished revisions
are compatible and each release has at least five known observations (also five
jointly valid observations for a selected ratio). Coverage and unavailable states
remain explicit. This threshold does not imply statistical significance; avoid
causal/regression conclusions from small cohorts. Responses cap outcomes at 20
with an explicit other bucket, declared categories/reasons at 20 and scopes at
four. Count totals are exact decimal strings; missing totals are null.
