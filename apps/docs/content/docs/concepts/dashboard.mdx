This guide describes the current web interface. Product 1.0 plans to evolve it
into Flowmark Studio: a contextual workspace connecting process exploration,
comparisons and evidence. Existing navigation below remains the actual behavior.

## Choose the question you want to answer

Use **Overview → Where to go next** to choose an investigation path:

- **Issues:** identify affected runs and gather evidence for an application investigation.
- **Insights:** determine which recorded measurements changed between two periods.
- **Runs:** find a known execution and take its identifiers and evidence to your application logs.

Each page groups its content into tabs. The selected tab is included in the URL,
so you can reload or share the same view. Switching tabs preserves the current
filters; it does not clear the investigation scope.
Opening a run from the history also keeps a return link to the same filtered
list, so you can inspect an execution and return to the affected population.

## Start with the workflow overview

The overview shows volume, run completion, failed-run count and p95 duration
for runs started in the last seven UTC days, compared with the previous seven.
**Health & attention** lists workflows and attention links; **Latest activity**
shows the latest runs. Open **Insights** for trends and
reported outcomes, and **Issues** for failure groups that need investigation.

## Browse workflows and runs

Open **Workflows** for a table grouped by name prefix. Search, filter by naming
namespace, or sort by name group or run count. Each page contains
at most 12 workflows. Selecting one opens tabs for **Overview**, **Runs**, **Reported results**,
**Confirmations**, **Diagnostics**, and **Configuration**.

Open **Runs** to search SDK run IDs, workflow names, last checkpoints,
correlation IDs or parent IDs. Combine workflow, status and naming-namespace
filters using the **Execution**, **Reported results**, **Business reference**,
and **Technical context** filter tabs. All groups narrow the same list, and
the applied-filter chips remain visible when switching groups.
Each page requests 25 runs. Enabled business-reference keys and declared
result fields can add an exact filter. Arbitrary JSON is not searchable.

Run history is the project's recorded runs, not only the overview's latest 100.
Metrics on the overview use their labelled populations. Insights and Issues
compare a 7- or 30-day UTC start window with the previous window of the same
length. Naming namespace is inferred from workflow name prefixes.

## Read trends and problems

**Insights** shows started-run volume, technical completion, duration, a
workflow breakdown and recorded changes. Choosing a workflow compares that
workflow's declared business outcomes inside the same window. Completion is not
a business success score, and a difference is not a cause.

**Issues** groups failed runs by workflow and terminal failure code. Each group
shows how often it happened, the previous window's count, when a run last
started, and links to the workflow and matching runs. Groups are calculated
when you open the page. Flowmark does not assign, acknowledge or resolve them.
Longer operation medians are recorded differences, not confirmed anomalies.

## Open an execution

Run details open on **Run summary**. Separate tabs keep investigation focused:

- **Run summary:** execution status, reported highlights and recorded milestones.
- **Reported results:** reported result, failure, last-reported progress, and evidence
  counts. Expand raw result data when needed.
- **Timeline:** filter event types and expand rows for occurrence/receipt
  times, operation timing, properties, progress and safe error details.
  Each page contains at most 15 events.
- **Context:** properties, environment, release and the external SDK run ID.
- **Compare:** this run versus up to 50 earlier runs of the same workflow.
  The default window is 30 days and the same environment. Duration is compared
  with the peer median and p95.
- **Related runs:** explicitly declared parent matches and correlated runs,
  paginated independently at 10 rows per table.
- **Confirmations:** application-declared expectations and observed resolutions,
  separate from technical completion.
- **Take findings forward:** copy an investigation summary with status, failure
  evidence, timestamps and identifiers, or export the run and timeline as JSON.

An investigation is useful when you can identify the execution, describe what
was observed and decide the next action in the owning application. Use the
summary as a factual handoff and add your diagnosis separately. It does not
claim a root cause or verified business correctness.

For an import, check the imported/skipped result first. For an interrupted sync,
inspect the last-reported progress and the failure. For an order failure,
inspect checkpoints before retrying work that may already have side effects.

## Settings and projects

**Settings** is where you rename or create a project, create, rotate, or
revoke ingestion keys, and update the signed-in name or password. A write key
is shown once. Emergency rotation revokes the selected write key immediately.
To overlap credentials, create a new key, update the application, then revoke
the old one. A project name does not restrict the environment a run reports.
The sidebar switches between projects you own. Dashboard sign-in does not
replace the SDK key.

## How to read a run

Completed means the application called `done()`. Failed means it called
`fail()`. A handled error can sit next to a completed run. Last-reported
progress is the latest snapshot your code sent.

## Connect to deeper investigation

Use stable, non-sensitive business identifiers in properties when you want to
look up the same work in your logs. [Related runs](/docs/concepts/related-runs)
use the IDs you pass. The [API guide](/docs/api) explains internal IDs and
project-scoped queries.
