The API is a Next.js application. The reference deployment is
[https://api.flowmark.dev](https://api.flowmark.dev). In local development it
runs at `http://localhost:3003` and requires PostgreSQL for event ingestion
and workflow queries. The dashboard is
[https://app.flowmark.dev](https://app.flowmark.dev).

## HTTP endpoints

| Endpoint                        | Purpose                                       |
| ------------------------------- | --------------------------------------------- |
| `GET /api/health`               | Database-independent API liveness check       |
| `GET /api/auth/*`               | Better Auth session lookup                    |
| `POST /api/auth/*`              | Better Auth sign-in, sign-out, and callbacks  |
| `POST /api/register`            | Create an owner, project, and first write key |
| `GET /api/trpc/{procedure}`     | Typed read/query API used by the dashboard    |
| `POST /api/trpc/{procedure}`    | tRPC transport; no mutations currently exist  |
| `OPTIONS /api/trpc/{procedure}` | Dashboard CORS preflight                      |
| `POST /v1/events`               | Private server-side workflow event ingestion  |
| `POST /v1/browser-events`       | Public-key browser event ingestion            |
| `OPTIONS /v1/browser-events`    | Browser CORS preflight                        |

The API application's root page (at your API origin; locally
`http://localhost:3003`) includes expandable request
examples, response codes, event schemas, and per-route security notes.
Examples are documentation only: the reference never sends writes or loads
credentials. The health-check link is a safe GET request.

Private ingestion uses a server write key in an `Authorization` header with
the `Bearer` scheme. The API validates event envelopes, resolves the project
from the key rather than from the request body, and acknowledges ingestion
only after persistence.

Browser ingestion uses a separate public browser key and an allowed request
Origin; it cannot read data or use private server ingestion. Request bodies are
limited to 64 KiB. Browser keys are limited to 120 requests per minute per key.
Workflow names are prefixed with `browser.`. Origin checks and CORS do not prove
identity outside a browser; treat browser telemetry as untrusted input, not
authoritative evidence of a business outcome.

## tRPC queries

The API router exposes these procedures at `/api/trpc`:

- `health.check`
- `project.snapshot`
- `workflow.list`
- `run.detail` (requires a run UUID)
- `run.related` (requires a run UUID)
- `run.compare` (requires a run UUID)

Use GET for these queries; the exported POST transport does not enable
query-over-POST. `run.detail` accepts `{ "id": "<UUID>" }` as the URL-encoded
`input` query parameter. Use the internal run `id` returned by
`project.snapshot`, not the external `runId` sent during ingestion. A missing
or differently scoped run returns an empty array, not a 404.
`run.related` takes the same internal run UUID and returns project-scoped
parent matches and correlated runs. `run.compare` returns the current run
and the last 20 peers of the same workflow, with peer success rate, median
duration, and p95 duration.

Dashboard reads use the signed-in Better Auth session. Query results and run
lookups are scoped to a project the user belongs to. The dashboard's
same-origin proxy forwards the session cookie; it does not put a read key in
browser code. Programmatic callers without a session may still send a project
read key in the `Authorization` header.

`run.detail` returns the append-only event timeline, including measured
operations (`operation_started`, `operation_completed`, `operation_failed`)
and absolute `progress` snapshots. Non-final `report` events carry a bounded
`result` snapshot. Timeline rows expose `receiptOrder` and `isLatestReport`; the
latest report uses server receipt order, not application timestamps. Report data
is separate from terminal results and excluded from final-result aggregates. Operation events include `operationId` and
`operationName`; terminal events include the monotonic `durationMs`. Progress
events include `completed`, optional `total`, and optional `unit`. Each event
also includes its occurrence `timestamp` and persistence `receivedAt`. Run
summaries and timeline rows include optional `correlationId` and `parentRunId`
declared at start.

`run.related({ id })` accepts the internal UUID of a run and returns
`{ parentMatches, related }`. Both lists are project-scoped to the authorized
project;
`related` includes every other run sharing the explicit correlation ID, not
only overview rows in the latest-100 snapshot. Parent matches resolve the
provided external `parentRunId` only within the same project. These are
application-declared associations, not causal proof or an OpenTelemetry trace.

## Current data and service limits

Events, runs, workflow definitions, and keys are stored in PostgreSQL through
the database package. Metrics are computed by the backend rather than accepted
as client-submitted aggregates. The dashboard currently shows the latest 100
runs, with volume, success rate, median and p95 duration, daily trends,
slowest operations, failure codes, and run comparison.

The seeded `local@dev` account is a loopback fixture for the operations
project, not a hosted owner. Registration creates a real local account and
project. Hosted API operations, key-rotation UI, alerting, and durable
offline delivery are not implemented.

## Declared business search

`run.list` accepts `workflow`, `businessKey` and `businessValue` for one exact
current-context predicate. Both business inputs and a workflow are required
together. Keys use ASCII letters, digits and underscores, start with a letter
and contain at most 64 characters. Values are non-empty strings up to 256
characters. Existing built-in filters, cursors and counts combine with the
business predicate; ordinary free-text search keeps its existing behavior.

Authenticated project members manage workflow search permissions using
`resultDeclarations.searchFields({ projectId, workflow })` and
`resultDeclarations.setSearchFields({ projectId, workflow, fields })`.
A field is `{ key, role: "lookup" }` or
`{ key, role: "dimension", values: ["crm-a", "crm-b"] }`. The array is a complete
replacement (at most eight distinct keys; one to twenty distinct category
values). An empty array disables all business search fields for that workflow.
This reuses workflow configuration boundaries alongside result declarations;
search permissions are mutable and do not reinterpret immutable result revisions.

Read-key callers may use enabled filters but cannot manage configuration.
Malformed filters are rejected; unconfigured, disabled, wrong-workflow or
out-of-vocabulary filters return an empty scoped result. Stored context is
matched using JSON string containment before event aggregation. Migration 0011
creates the scoped configuration table and a GIN index over run properties.
Apply it before deploying the accepting API. Index creation scans existing runs
and can block writes; verify its duration in isolated Preview before merge.
Production rollout and npm publication remain separate operations.

## Event acknowledgments and terminal ordering

Private and direct browser ingestion return HTTP 202 with `accepted` and
`disposition`: `recorded` for a new persisted event, `duplicate` for an existing
event ID in that execution, or `ignored` for repeated starts/ordinary late
markers. Ignored receipts have `accepted: false`; they are not new evidence.

A new completed/failed event after any terminal is HTTP 409 with
`{ accepted: false, disposition: "conflict", code: "EVENT_CONFLICT" }`.
Event-ID collisions with another execution also return a generic conflict,
without foreign identifiers. Missing starts use HTTP 409 `RUN_NOT_FOUND`.
Duplicate IDs are checked before terminal decisions, so a real terminal retry
remains idempotent. Reusing an ID never amends its original payload.

First terminal accepted by persistence wins, independent of application clock
order. Transaction-scoped locks reserve envelope identities and serialize writes
per run; these only coordinate telemetry. Final results/outcomes and all original
start metadata remain stable. Older stored mixed terminals retain their failed
projection. No backfill/schema migration is required; deploying the accepting
backend changes future writes. Older backends still use their existing policy.

## Business outcome reads

`project.businessInsights` accepts a workflow, revision, declared field `path`,
`currentStartedAfter`/`currentStartedBefore` and
`previousStartedAfter`/`previousStartedBefore`. Use canonical ISO UTC timestamps
with milliseconds; each half-open interval is at most 31 days. Optional
`numerator`/`denominator` paths must both be aggregatable count fields. Optional
`releaseA`/`releaseB` select distinct releases. Optional `businessKey`/
`businessValue` must select a configured bounded dimension, not a lookup key.
Reads use the signed-in project or authenticated read-key project.

Immutable result declaration fields can opt into `aggregate: true`. Categories
and reason maps also require `values` with 1–20 distinct allowed strings. Older
presentation declarations are not automatically aggregatable. The accepting
API/dashboard must be deployed together; this metadata uses existing JSON storage
and needs no schema migration or SDK runtime publication.

The bounded response includes current/previous and optional release scopes,
finished/open/technical-failure populations, field coverage, canonical outcome
counts, selected field/category/reason totals, daily cohorts and a weighted ratio.
Totals are exact decimal strings or null. Ratio pairs exclude missing/wrong-type
members; zero overall denominator yields null. Release comparison reports
availability and its minimum known-run threshold. See [metric definitions](/docs/concepts/insights).

`run.list` adds `outcome`, `definitionRevision`, `terminalOnly`, canonical UTC
`startedBeforeExclusive` and `resultSelection`:

```ts
const page = await client.run.list({
  workflow: "import.products",
  startedAfter: "2026-10-20T00:00:00.000Z",
  startedBeforeExclusive: "2026-10-27T00:00:00.000Z",
  resultSelection: {
    revision: "import-v2",
    path: ["imported"],
    operator: "gte",
    value: 1,
  },
  limit: 25,
})
```

Result predicates imply finished runs and the specified original-start revision.
Count operators are eq/gte/lte; categories require string eq; reason predicates
also provide a declared `reason` key. Unknown paths/revisions, incompatible
operators and undeclared reason/category values are rejected. Queries never
accept arbitrary JSON SQL. Existing inclusive `startedBefore` remains available;
evidence uses the additive exclusive bound to reproduce the aggregate exactly.

For weighted-ratio evidence, `run.list` also accepts `ratioSelection` with
`revision`, `numerator` and `denominator` paths. Both paths must be declared
aggregatable counts; only jointly valid finished observations match. It combines
with period/dimension/release filters and uses the same count/pagination rules.
This is the population behind a ratio, rather than two independently filtered
lists with different missing values.

## Peer comparison selection

Existing `run.compare({ id })` calls continue to work. Optional `selection`
accepts `days` (integer 1–90, default 30), `environment` (`same` or explicit `all`),
`sameRelease` and a paired `dimensionKey`/`dimensionValue`. Dimensions must be
currently configured bounded values for this workflow/project; lookup keys and
unconfigured values are rejected. Authorization precedes comparison reads.

Peers are strictly earlier by (startedAt, internal ID), in the same workflow;
missing environments/releases match only missing values under matching filters.
The response adds population metadata with eligible count, selected count (cap
50), filters and descriptive sample threshold 5. Existing longest-occurrence
operation fields remain; additive current occurrence/open/failed counts,
per-occurrence median and total recorded duration distinguish repeated work.
Totals across overlapping operations are not elapsed run time. No SDK or schema
migration is required. The default baseline intentionally no longer mixes all
environments or includes later runs.

## Explicit application-owned attempts

See [Attempts and retries](/docs/reference/attempts) for operation `attempt: { groupId, number }`, qualified new-run `retryOf` links, bounds, project scoping and the required `attempts-v1` accepting-server acknowledgment. Supplying these options is explicit opt-in; deploy accepting storage/API/readers before enabling them. Transport retries remain separate from business attempts.

## Expectation evidence

[Expected confirmations](/docs/reference/expectations) require the accepting `expectations-v1` server and migrations. Resolve/cancel are explicit, project-scoped evidence reports and may follow a terminal run without changing its outcome/result. Direct browser evidence stays untrusted; the existing generic server-key proxy rejects expectation events. Deadlines are evaluated on read from server observation, without background notifications or a retention extension.

The authenticated `run.expectations({ id })` read returns one server `asOf`, declared states, unmatched settlements and evidence availability. `run.list` accepts `expectationState`; its bounded `attention` population counts runs separately from expectations. State discovery defaults to 30 days, allows at most 90 days and uses page sizes 1–100. Raw `/v1/events` expectation writes require both a secret write key and `X-Flowmark-Expectations: v1`; server SDKs set the marker automatically. It is not a separate credential.
